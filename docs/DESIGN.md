## 確定した技術構成

```text
React + TypeScript + Vite（PWA）
              ↓ REST API（HTTP + JSON）
Django + Django REST Framework
              ↓ ORM
          PostgreSQL
```

- フロントエンド: React + TypeScript
- ビルドツール: Vite
- バックエンド: Django + Django REST Framework
- データベース: PostgreSQL
- アプリ形態: PWA
- 音声: Web Audio APIで生成する学習音、休憩音、通知音

### 採用理由

- タイマー、音声、円形表示はブラウザ上の操作が中心なのでReactを使用する。
- TypeScriptでタイマー状態とAPIデータの型を明示する。
- SEOやサーバー側画面生成を主目的としないため、Next.jsは使用しない。
- Djangoの認証、ORM、マイグレーション、管理画面、セキュリティ機能を利用する。
- Django REST FrameworkでReact向けのJSON API、入力検証、認証・権限確認を実装する。
- PostgreSQLで利用者、テーマ、学習記録、振り返りを関連付け、期間集計する。

## 役割分担

### React + TypeScript

- タイマー画面と学習記録画面を表示する。
- 開始、一時停止、再開、休憩、待機などの画面状態を管理する。
- 終了予定時刻との差から残り時間を計算する。
- 円形タイマーを描画する。
- Web Audio APIでブラウンノイズ、休憩用環境音、通知音を制御する。
- 振り返りフォームを段階的に有効化する。
- REST APIを呼び出し、読み込み中・成功・失敗を表示する。
- PostgreSQLへ直接接続しない。

### Django

- 利用者、ログイン状態、セッションを管理する。
- モデルとマイグレーションでデータ構造を管理する。
- 利用者が自分のデータだけを操作できるよう認可する。
- 日、週、月、累計の集計ルールを持つ。
- 管理画面と共通のセキュリティ機能を提供する。

### Django REST Framework

- Djangoの機能をReactから利用できるHTTP APIとして公開する。
- JSONとDjangoモデルの間を変換する。
- API入力を検証し、不正な値を拒否する。
- URL、HTTPメソッド、レスポンス、エラー形式を揃える。
- APIごとに認証と権限を確認する。

### PostgreSQL

- 利用者、学習テーマ、学習記録、振り返り、深掘り項目を永続保存する。
- 秒単位の学習時間を保持する。
- 日付や利用者、テーマによる検索・集計を支える。

## データ保存の基本方針

- 1秒ごとにAPI通信しない。
- タイマー表示はReact内で更新する。
- 一時停止、再開、終了などの節目で必要な状態を保存する。
- 学習終了時、Reactは計測結果をAPIへ送る。
- Djangoは値、ログイン利用者、対象データの所有者を検証してから保存する。
- 集計結果はPostgreSQLの保存データを基準とし、React内の値だけを正としない。

## REST APIの位置付け

RESTは製品名ではなく、HTTP上で対象となるデータをURLとして扱う設計方法である。

例:

```text
GET    /api/study-records/     学習記録を取得
POST   /api/study-records/     学習記録を作成
GET    /api/study-records/42/  42番の学習記録を取得
PATCH  /api/study-records/42/  42番の学習記録を一部更新
DELETE /api/study-records/42/  42番の学習記録を削除
```

ReactとDjangoは主にJSON形式でデータを交換する。具体的なURLはAPI設計で確定する。

## 認証とアカウント復旧

- 初期版はメールアドレスとパスワードによる登録・ログインを使用する。
- `AbstractUser`を継承した独自ユーザーモデルを最初のマイグレーション前に作成する。
- ユーザー名は使用せず、一意なメールアドレスをログインIDにする。
- メールアドレスは前後の空白を除いた入力表記を保存する。登録時の重複確認とログイン時の検索では大文字・小文字を区別しない。
- 独自ユーザーマネージャーのログイン検索を大文字・小文字を区別しない検索にし、PostgreSQLにもメールアドレスを小文字化した値への一意制約を設定する。画面側の確認だけに依存せず、同時登録でも重複を防ぐ。
- Django REST Frameworkのセッション認証を使用する。
- ブラウザのCookieにはパスワードやメールアドレスではなく、セッションを識別するランダムなキーを保持する。
- セッションの内容はDjango側で管理し、パスワードはユーザーテーブルにハッシュとして保存する。
- Reactはデータを変更するリクエストでCSRFトークンを`X-CSRFToken`ヘッダーに設定する。
- 新規登録とログインを含む状態変更APIにもCSRF対策を適用する。
- セッションCookieは`HttpOnly`とし、本番環境では`Secure`を有効にする。`SameSite`と許可するオリジンはデプロイ構成に合わせて限定する。
- ログアウト時はDjango側のセッションを無効にする。
- Django標準のパスワード検証機能を有効にし、短いパスワード、一般的すぎるパスワード、数字だけのパスワードなどを拒否する。
- ログインと新規登録にはAPI単位の試行回数制限を設け、短時間の総当たりと大量登録を抑える。
- 初期版ではメールアドレスの本人確認を行わない。
- GoogleログインとGitHubログインは初期版に含めない。
- 初期版では、管理者がDjango管理画面から既存利用者のパスワードを変更できるようにする。
- パスワード変更時は利用者レコードを作り直さないため、学習時間と振り返りは保持される。
- 利用者自身がメールのワンタイムリンクから行うパスワード再設定は、一般公開時の追加候補とする。
- 新規登録画面に簡潔なプライバシー説明を表示し、メールアドレスと振り返りを保存すること、管理者が障害対応など運用上必要な場合に保存内容へアクセスできることを明示する。
- 初期版で利用者からデータ削除の依頼があった場合は、管理者がDjango管理画面から対応する。

## 画面一覧と画面遷移

### 初期版の画面

1. タイマー画面
2. ログイン画面
3. 新規登録画面
4. 学習記録画面
5. 振り返り入力・編集画面
6. 学習記録詳細画面

### 共通方針

- タイマー設定、学習中、休憩中、待機中は同じタイマー画面内の状態として切り替える。
- 初回の未ログイン利用者には、ログイン、新規登録、ログインせずタイマーを使う選択肢を分かりやすく表示する。
- 「ログインせずタイマーを使う」を選ぶと認証案内を閉じ、そのままタイマーを利用できる。
- ゲスト利用中も、必要になった時にログインへ移動できる控えめな入口は残す。
- 振り返りフォームは入力項目と文章量が多いため、モーダルではなく独立画面にする。
- 振り返りの入力欄は複数行を前提とし、長文の入力と全文確認ができる大きさにする。
- 保存後の振り返り文章は編集可能にするが、計測済みの学習時間は編集不可とする。
- 「学習時間を保存せず終了」だけは、実行前に確認モーダルを表示する。
- タイマー動作中は、ログイン、ログアウト、学習記録画面への移動を無効にし、終了後に操作できることを表示する。
- ゲストとして開始したタイマーは、その途中でログイン利用者のタイマーへ変更しない。

### 学習終了後

- 未ログイン時は終了方法を選ぶモーダルを表示せず、音と計測を止めてタイマーを初期状態へ戻す。
- ログイン中は「学習時間を保存して振り返る」「学習時間を保存して終了」「学習時間を保存せず終了」を表示する。
- 「学習時間を保存して振り返る」は時間を保存して振り返り入力画面へ移動し、保存後に記録詳細を表示する。
- 「学習時間を保存して終了」は時間だけを保存し、保存完了状態を表示する。
- 「学習時間を保存せず終了」は確認後に記録を破棄し、破棄完了状態を表示する。
- 保存完了状態では今回の学習時間と、学習記録または新しい学習への入口を表示する。
- 破棄完了状態では学習時間や学習記録への入口を表示しない。
- WebページやPWAからウィンドウを確実に自動終了できないため、利用者がウィンドウの閉じる操作を行う。

### 保存データの確認方法

- 通常利用者は学習記録画面で、日・週・月・累計の集計と日付ごとのセッションを確認する。
- 学習記録画面には新しい日付から順に、日付とその日の合計学習時間を並べる。
- 日付を選ぶと、その日に保存したセッションの一覧を表示する。
- セッションを選ぶと学習記録詳細画面を開き、学習時間と振り返り全文を確認する。
- 初期版ではカレンダーを作らず、日付別の一覧を使用する。
- 今日・週・月・累計は表示中のページから足すのではなく、Djangoが現在の利用者の保存済みセッション全体をPostgreSQLで集計する。
- タイマー画面の「今日」は、APIから取得した今日の保存済み時間にReact内の今回の未保存時間を加えた暫定値とする。
- 今回の学習時間を保存せず終了した場合は、React内の今回分を暫定値から除く。
- 管理者はDjango管理画面から利用者、学習記録、振り返りの保存状態を確認できる。
- Django管理画面の一覧には振り返り本文をそのまま表示せず、管理に必要な識別情報、日時、学習時間を中心に表示する。
- Django管理画面へ入れるアカウントは必要最小限の管理者に限定する。
- 通常利用者がPostgreSQLを直接操作する画面は作らない。
- 将来AIで傾向や弱点を分析する場合は、保存済みの構造化データをAPIまたはエクスポート機能から渡す。初期版には含めない。

## タイマーの通常状態

- `開始前`: プリセットを選択し、最初の学習を開始できる。
- `学習中`: 学習時間とブラウンノイズが進行する。一時停止または学習終了ができる。
- `学習一時停止中`: 学習時間と音を止める。再開または学習終了ができる。
- `休憩中`: 休憩タイマーと休憩用環境音が進行する。一時停止、休憩の切り上げ、学習終了ができる。
- `休憩一時停止中`: 休憩の残り時間と音を止める。休憩再開、休憩の切り上げ、学習終了ができる。
- `次の学習待機中`: 休憩完了後に自動学習せず待機し、利用者の操作で次の学習を開始する。
- `終了方法選択中`: ログイン中の利用者が保存方法を選択する。
- `終了完了`: 保存または破棄の結果を表示する。

再生・一時停止の主操作は同じ位置に表示し、状態に応じてアイコンを切り替える。

- 開始前: 再生アイコン
- 学習中: 一時停止アイコン
- 学習一時停止中: 再生アイコン
- 休憩中: 一時停止アイコン
- 休憩一時停止中: 再生アイコン
- 次の学習待機中: 再生アイコン

アイコンには`aria-label`などの読み上げ用の名前と、マウスを置いた場合の短いツールチップを付ける。画面上に「学習を再開」「休憩を再開」などの文字は常時表示しない。

`学習を終了`はアプリ内の操作であり、ブラウザまたはPWAのウィンドウを閉じる操作とは分ける。

## タイマーの復元方針

- 動作中のタイマーは約5秒ごとにブラウザ内へ復旧用の状態を一時保存する。
- 一時停止、再開、学習・休憩の切り替えなど、状態が変わる操作時にも保存する。
- 復旧用の一時保存はPostgreSQLへの正式な学習記録ではなく、API通信も行わない。
- 正式な学習記録は、ログイン中の利用者が終了方法で保存を選んだ場合にPostgreSQLへ保存する。
- 復旧用には、今回の累計学習時間、学習・休憩の区別、残り時間、プリセット、25分／5分設定の完了回数を保持する。
- 動作中と一時停止中の区別は復旧用に保持せず、再起動後は必ず中断状態にする。
- 復元画面では「前回の続きから再開」または「終了方法を選ぶ」を利用者が選ぶ。
- 続きから再開する場合も自動再生せず、利用者の明示的な操作でタイマーを動かす。
- 終了方法を選んだ場合は、学習時間を保存して振り返る、学習時間を保存して終了、学習時間を保存せず終了から選択する。
- 強制終了時は最後の一時保存以降の数秒を失う可能性を許容し、閉じていた時間の過大加算を防ぐことを優先する。
- 正常に終了、保存または破棄した復旧用データは削除する。
- 学習終了予定時刻を過ぎてから画面処理が再開した場合は、学習終了予定時刻までだけを学習時間へ加算する。
- 画面処理の再開時に休憩終了予定時刻も過ぎていた場合は、次の学習を開始せず待機状態にする。
- OSスリープ中の正確な判定は保証せず、少なくとも1回分の設定学習時間を超えて自動加算しない。
- 同じブラウザで別タブまたはPWAウィンドウのタイマーが動作している場合は、新しいタイマーを開始せず既存タイマーの存在を表示する。
- タイマーの排他状態には定期更新するブラウザ内の識別情報を使い、異常終了後は一定時間で古い排他状態を解除できるようにする。

## データモデル

### 関係

```text
利用者 1 ── 0以上 学習テーマ
利用者 1 ── 0以上 学習記録
学習テーマ 1 ── 0以上 学習記録
学習記録 1 ── 0または1 振り返り
振り返り 1 ── 0以上 深掘り項目
```

### 利用者 `User`

- `AbstractUser`を継承する。
- 一意なメールアドレスをログインIDにする。
- メールアドレスの入力表記は保持し、認証と一意性判定だけ大文字・小文字を区別しない。
- Django標準のパスワード、権限、アカウント状態、登録日時を利用する。

### 学習テーマ `StudyTheme`

- 所有する利用者
- テーマ名
- 作成日時、更新日時
- 初期版では利用者ごとに「プログラミング」を用意する。
- 学習テーマの所有者と学習記録の利用者が一致することをDjango側で検証する。

### 学習記録 `StudyRecord`

- 利用者
- 学習テーマ
- Reactが保存単位ごとに生成する重複防止用UUID
- 学習日（タイマーを開始した日）
- 実際の開始日時、終了日時
- 学習秒数
- 使用したプリセット
- 設定した学習時間と休憩時間
- 25分／5分設定の完了回数
- 作成日時、更新日時

同じ利用者と同じ重複防止用UUIDの組み合わせには、データベースの一意制約を設定する。API側の事前確認だけに依存せず、同時リクエストでも二重登録を防ぐ。

タイマーを開始してから利用者が明示的に終了するまでを1件とする。途中の休憩、一時停止、待機は学習秒数へ含めない。学習時間を保存せず終了した場合は作成しない。

### 振り返り `Reflection`

- 対象の学習記録（1対1）
- 今回取り組んだこと
- 引っかかったこと
- 引っかかったことに対して試したこと
- 試した結果、理解はどう変わったか
- 次に行う具体的な行動
- 作成日時、更新日時

学習時間を保存して終了した学習記録には振り返りを作らない。同じ日に複数回振り返った場合も、学習記録ごとに別々に保存する。

全項目が空欄の場合は振り返りを作成しない。振り返りがない学習記録には、詳細画面から後で振り返りを作成できる。

### 深掘り項目 `ReflectionDeepDive`

- 対象の振り返り
- 内容
- 表示順
- 作成日時、更新日時

### 集計

- 日、週、月、累計の合計値を別テーブルへ保存しない。
- 現在の利用者とテーマに属する学習記録の学習秒数をPostgreSQLで合計する。
- 学習日を基準に期間を絞り込む。
- 日付をまたぐ学習は、初期版ではタイマーを開始した日に全時間を計上する。

## REST API

### 認証

```text
POST /api/auth/register/  新規登録
POST /api/auth/login/     ログイン
POST /api/auth/logout/    ログアウト
GET  /api/auth/me/        現在のログイン利用者を確認
GET  /api/auth/csrf/      CSRFトークンを取得
```

### 学習記録と集計

```text
GET    /api/study-records/            自分の学習記録一覧
GET    /api/study-records/?date=...   指定日の学習記録
POST   /api/study-records/            学習記録を作成
GET    /api/study-records/{id}/       学習記録の詳細
DELETE /api/study-records/{id}/       学習記録を削除
GET    /api/study-stats/              日・週・月・累計を取得
GET    /api/study-days/?page=...      日付別の合計を20日分ずつ取得
```

- 学習時間の数値だけを後から編集するAPIは作らない。
- 学習記録の削除前にはReact側で確認を表示する。
- 学習記録を削除すると、関連する振り返りと深掘り項目もデータベースの関連設定により削除する。
- 削除後の期間集計は残っている学習記録から再計算する。
- Reactは学習記録の保存単位ごとにUUIDを生成し、作成APIへ含める。
- 同じ利用者から同じUUIDの作成要求を再受信した場合は、新しい記録を増やさず既存の記録を返す。
- これにより、通信切断や応答待ちの失敗後に再送しても、同じ学習記録の二重登録を防ぐ。
- 学習記録一覧と日付別一覧は新しい順とし、ページ単位で取得する。

### 振り返り

```text
POST  /api/study-records/{id}/reflection/  振り返りを作成
PATCH /api/study-records/{id}/reflection/  振り返りを編集
```

- 深掘り項目は振り返りのJSON内に順番付きの配列として含める。
- 学習時間を保存して振り返る場合は、最初に学習記録を作成し、返されたIDを使って振り返りを作成する。
- 振り返り保存に失敗しても学習記録は保持し、振り返りだけを再送できるようにする。
- 深掘り項目の編集では、送信された順番付き配列を1回のデータベース処理でまとめて置き換える。
- 前提欄を消す操作では、後続欄を消すことをReact側で確認し、Django側でも矛盾した組み合わせを拒否する。

### 利用者の特定と権限

- Reactから利用者IDを受け取って所有者を決めない。
- Djangoは各リクエストのセッションCookieから`request.user`を特定する。
- 学習記録の作成時は`request.user`を所有者として設定する。
- 一覧、詳細、編集、削除は`request.user`が所有するデータだけを対象にする。
- 他の利用者のIDをURLへ指定しても、その記録の存在が分からないよう404を返す。

## 音声

### 学習中の音

- ブラウンノイズは音源ファイルを繰り返さず、Web Audio APIでリアルタイム生成する。
- 音の開始は利用者が再生ボタンを押した操作を起点にし、必要に応じて`AudioContext`を再開する。
- 一時停止、学習終了、休憩への切り替え時はブラウンノイズを停止する。

### 休憩用環境音

- 休憩用環境音も音源ファイルを同梱せず、Web Audio APIでリアルタイム生成する。
- 雨音、水音、柔らかい風音などを候補とし、眠る前にも聞ける穏やかな音を目標にする。
- 学習中のブラウンノイズとは生成処理を分離し、休憩音だけを後から調整または交換できる構成にする。
- 初期実装後に実際の音を確認し、不快な音や繰り返し感がある場合は生成パラメーターや生成方式を変更する。
- MP3などの外部音源は初期版に同梱せず、音源ライセンスの管理を不要にする。

### 通知音と音量

- 休憩終了前5秒のカウントダウン音と完了音はWeb Audio APIで生成する。
- カウントダウン音と完了音は聞き分けられる音にする。
- ブラウンノイズ、休憩用環境音、通知音へ共通の音量設定とミュートを適用する。
- タブを切り替えた場合も可能な範囲で再生を継続するが、ブラウザやOSによる制限はPWA設計で扱う。

## PWAとバックグラウンド動作

### インストールと表示

- Web App Manifestにアプリ名、アイコン、開始URL、テーマ色を定義する。
- 表示モードは`standalone`とし、デスクトップのアイコンから独立したウィンドウで起動できるようにする。
- 初期版はデスクトップ版Chrome系ブラウザを主な確認対象とする。
- PWAはReact画面をアプリのように表示する仕組みであり、DjangoとPostgreSQLは引き続きサーバー側で動作する。

### キャッシュとオフライン

- Service WorkerでReactの画面やアイコンなどの静的ファイルをキャッシュする。
- 初回アクセスとPWAのインストールにはインターネット接続を必要とする。
- 初回読み込み後は、通信がなくてもゲスト用タイマーの基本操作を可能にする。
- 認証、正式な学習記録の保存、集計、履歴確認にはサーバー通信を必要とする。
- APIレスポンスをService Workerで無条件にキャッシュせず、別利用者の記録が表示される危険を避ける。
- 保存時に通信できない場合は、未送信の学習結果をブラウザ内に保持し、接続回復後に利用者が再送できるようにする。
- 未送信データを保持している間は、正式保存が完了していないことを明示する。
- 復旧用状態と未送信データは、ゲスト用とログイン利用者ごとに保存領域を分ける。
- 別の利用者がログインした場合は、前の利用者の未送信データを表示・送信しない。
- 正式保存または破棄が完了したデータは、対応する利用者のブラウザ内保存領域から削除する。

### タイマーとバックグラウンド

- Service Workerを常時動作するタイマーとして使用しない。Service Workerはブラウザの判断で停止されるためである。
- タイマーはReact側で管理し、1秒ごとの回数ではなく開始時刻・終了予定時刻との差から時間を計算する。
- タブ切り替えやウィンドウ最小化で画面更新が遅れた場合も、処理が再開した時点の時刻から表示と状態を補正する。
- アプリが開いていてOSが動作中である場合は、音声とタイマーを可能な範囲で継続する。
- ブラウザ、PWA、OSによるバックグラウンド停止やスリープ中の動作は保証しない。
- OSスリープ中の動作を保証するためだけの常駐処理、通知、画面スリープ防止は初期版に含めない。

### 終了と復旧

- 約5秒ごとの復旧用保存に加え、画面が非表示になる`visibilitychange`でも最新状態をブラウザ内へ保存する。
- `unload`や`beforeunload`だけに依存した最終保存は行わない。
- ブラウザまたはPWAを閉じた後の時間を学習時間へ加算しない。
- 再起動時は保存済みの復旧状態を中断状態として提示し、自動再生しない。
- Web Push、バックグラウンド通知、OS通知は初期版に含めない。

## エラー処理

### 学習記録と振り返りの保存

- 保存ボタンを押した後は処理中であることを表示し、同じボタンの連打を無効にする。
- 学習記録の正式保存が成功するまで、今回の計測結果をブラウザ内から削除しない。
- 通信失敗時は入力内容と計測結果を保持し、再送できるようにする。
- 再送時は同じ重複防止用UUIDを使用し、二重登録を防ぐ。
- 学習記録の保存に成功し、振り返りの保存だけに失敗した場合は、学習記録を残したまま振り返りだけを再送する。
- 失敗時に「保存できませんでした」だけで終わらせず、再試行できるか、入力を修正すべきかを表示する。

### APIと認証

- 入力値の誤りは、該当する入力欄の近くにメッセージを表示する。
- 未ログインまたはセッション切れの場合は、未保存内容を保持したままログインが必要であることを表示する。
- 他の利用者の学習記録を指定した場合は、存在の有無を明かさず404を返す。
- サーバー内部エラーでは、利用者へ内部の例外内容やスタックトレースを表示しない。
- Django側には原因調査に必要なログを残すが、パスワード、セッションキー、振り返り本文を通常ログへ出さない。

### タイマー、音声、ブラウザ保存

- 音声の開始に失敗してもタイマー自体は動かし、音声を再度有効にする操作を表示する。
- ブラウザ内への復旧用保存に失敗した場合は、タイマーを止めず、復旧できない可能性を警告する。
- 予期しない画面エラーでは、可能な限り復旧用データを残し、再読み込みの案内を表示する。
- オフライン状態とサーバーエラーを区別し、オフラインの場合は接続回復後の再送を案内する。

## 最低限のテスト

### Django・APIの自動テスト

- 新規登録、ログイン、ログアウト、現在の利用者取得。
- 登録時と異なる大文字・小文字でも同じメールアドレスでログインできること。
- 大文字・小文字だけが異なるメールアドレスを重複登録できないこと。
- 未ログイン利用者が保存済み学習記録へアクセスできないこと。
- 利用者が他人の学習記録を取得・削除できないこと。
- 学習記録の作成、一覧、詳細、削除。
- 同じ重複防止用UUIDを再送しても1件だけ保存されること。
- 日、月曜始まりの週、月、累計の集計。
- 学習記録の削除後に集計が変わり、振り返りと深掘り項目も削除されること。
- 振り返りの作成・編集と、深掘り項目の順番が保持されること。
- 負の学習秒数、終了日時が開始日時より前など、不正な値を拒否すること。

### Reactの自動テスト

- 学習完了後に休憩へ移ること。
- 25分／5分設定の4回目だけ長休憩へ移り、長休憩後に回数がリセットされること。
- 休憩終了後は次の学習を自動開始せず、待機状態になること。
- 一時停止、休憩、待機中の時間が学習時間へ加算されないこと。
- 途中終了では完了回数が増えず、経過した学習時間だけが残ること。
- 現在時刻と終了予定時刻から、バックグラウンド復帰後の残り時間を補正できること。
- 学習と休憩の両方の終了予定時刻を過ぎて復帰した場合、次の学習を自動開始せず待機状態になること。
- 同じブラウザの2画面でタイマーを同時開始できないこと。
- 合計時間は秒を保持しながら分表示を切り捨て、個別記録の1分未満を正しく表示すること。

ReactはVitest、Django REST Frameworkは`APITestCase`を使用する。初期版では大規模な画面自動操作テストを追加せず、ログイン、タイマー、保存、振り返り、PWA起動、音声を手動確認項目として残す。

## 開発環境

### 使用バージョン

- Node.js 22 LTS
- Python 3.13
- Django 5.2 LTSの最新パッチ
- PostgreSQLの公式Dockerイメージ

手元にはNode.js 22、Python 3.13、Dockerが導入済みであり、この構成をそのまま利用できる。Djangoは新機能の多さより長期サポートと安定性を優先し、5.2 LTSを使用する。

### リポジトリ構成

```text
pomodoro-reflection/
├── frontend/          React + TypeScript + Vite PWA
├── backend/           Django + Django REST Framework
├── docs/              要件・設計・学習記録
├── compose.yaml       ローカルPostgreSQL
├── .env.example       必要な環境変数の例
└── README.md
```

- 1つのGitリポジトリにフロントエンドとバックエンドを置く。
- Pythonは標準の`venv`と`requirements.txt`を使用し、初期版では新しいパッケージ管理ツールを増やさない。
- Node.js依存関係はnpmと`package-lock.json`で固定する。
- 機能実装中はDockerをローカルPostgreSQLだけに使用し、ReactとDjangoはホスト上で直接起動する。
- ローカルで初期版の機能が完成した後、本番デプロイ用にReactのビルド成果物とDjangoをまとめたDockerイメージを作成する。
- 開発中はViteの`/api`プロキシからDjangoへ接続し、ブラウザから同一オリジンに見える構成にする。
- パスワード、Djangoの秘密鍵、データベースURLは`.env`へ置き、Gitへ登録しない。
- `.env.example`には値を含めず、必要な変数名だけを記載する。

### 日付とタイムゾーン

- Djangoは`USE_TZ = True`とし、日時をデータベースへUTCで保存する。
- 初期版の表示・学習日・週・月の区切りは`Asia/Tokyo`を使用する。
- 日付をまたぐ学習記録は、東京時間における開始日の記録とする。
- 利用者ごとのタイムゾーン設定は一般公開時の追加候補とする。

## 本番環境とデプロイ

### 配置

```text
ブラウザ / インストール済みPWA
             ↓ HTTPS（同じURL）
Cloud Run: Django + REST API + Reactのビルド成果物
             ↓ TLS接続
Neon: PostgreSQL
```

- Reactを別の配信サービスへ分離せず、ビルド済みファイルをDjangoと同じCloud Runサービスから配信する。
- 静的ファイルはWhiteNoiseを使用してDjangoから配信する。
- 本番サーバーはDjangoの開発用`runserver`ではなくGunicornを使用する。
- 同じURLから画面とAPIを配信し、セッションCookie、CSRF、CORSの構成を単純に保つ。
- NeonのPostgreSQLは無料枠から開始する。
- Cloud Runはリクエスト課金、最小インスタンス数0、最大インスタンス数1から開始する。
- 最初は手動でCloud Runへデプロイし、正常稼働を確認した後に必要であればCloud Buildによる自動デプロイを追加する。
- Terraformは初期版で使用しない。GCPの画面または`gcloud`コマンドで設定する。
- Artifact Registryには古いDockerイメージを残し続けず、クリーンアップ方針を設定する。
- GCPの予算通知とCloud Runの支出上限を設定し、意図しない課金を抑える。

### 本番設定

- `DEBUG = False`にする。
- `SECRET_KEY`、`DATABASE_URL`、許可ホスト、CSRF許可元を環境変数から取得する。
- HTTPS用の`Secure` Cookie設定を有効にする。
- Dockerイメージの作成時にReactをビルドし、Djangoの`collectstatic`を実行する。
- データベースマイグレーションはWebコンテナの起動ごとに実行せず、デプロイ時の明示的な1回の処理として実行する。
- デプロイ前後に`python manage.py check --deploy`と主要な自動テストを実行する。
- Django管理者アカウントは環境変数へパスワードを固定せず、デプロイ後に安全な方法で作成する。
- 学習音、休憩音、通知音はWeb Audio APIで生成し、音源アップロード機能は作らない。

### Gitと公開手順

- 実装開始時からローカルGitで変更を小さく記録する。
- 最初の動作する骨組みができた段階でGitHubリポジトリへ接続する。
- APIキー、秘密鍵、`.env`、ローカルデータベースをGitHubへ登録しない。
- READMEには目的、主要機能、技術選定理由、構成図、セットアップ方法、テスト方法、デプロイ先を記載する。
- ポートフォリオ公開前に、テスト用アカウントや個人的な振り返りデータを本番データベースへ残していないか確認する。
