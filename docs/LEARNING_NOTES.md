# 開発学習メモ

実装中に理解した内容を、将来の記事や面接説明に使える形で追記する。

## Djangoのセッション認証

ログインに成功すると、Djangoは推測しにくいセッションキーを発行する。ブラウザのCookieへ保存するのはパスワードやメールアドレスではなく、このセッションキーである。以後のAPIリクエストではCookieが自動送信され、Djangoがセッションキーから利用者を特定して`request.user`へ設定する。

ログアウト時はDjango側のセッションを無効化する。ブラウザ側で表示だけを未ログインへ変える方法では、サーバー上のログイン状態が残るため不十分である。

## セッション認証とCSRF対策

Cookieはブラウザから自動送信されるため、別の悪意あるページから意図しない変更リクエストを送られる可能性がある。CSRF対策では、Djangoが発行したトークンをReactが`X-CSRFToken`ヘッダーへ設定し、Cookieとトークンの組み合わせが正しい場合だけ新規登録、ログイン、ログアウトなどの変更操作を受け付ける。

開発中は`localhost:5173`と`127.0.0.1:5173`を別のオリジンとして扱う点にも注意する。利用中のURLが`CSRF_TRUSTED_ORIGINS`にない場合、正しいトークンを送ってもDjangoはリクエストを拒否する。

## メールアドレスの大文字・小文字

入力されたメールアドレスの表記は保持しながら、ログイン検索と重複確認では大文字・小文字を区別しない。画面上の事前確認だけでは同時登録を完全に防げないため、PostgreSQLにも小文字化したメールアドレスの一意制約を設定する。

## ログイン試行回数の制限

ログインAPIは1分間に10回、新規登録APIは1時間に5回までとし、短時間の総当たりと大量登録を抑える。初期版はDjangoのキャッシュを利用する軽量な制限であり、複数サーバーへ拡張する場合は共有キャッシュを利用する。

## 記録予定

- Web Audio APIでブラウンノイズを生成する仕組み
- Web Audio APIで休憩用環境音を生成し、音源ファイルを不要にする仕組み
- ブラウザのタイマーがバックグラウンドで制限される理由
- 1秒ずつ減算せず、時刻の差から残り時間を計算する理由
- PWAと通常のWebアプリの違い
- Django認証でパスワードを安全に扱う仕組み
- 独自ユーザーモデルを最初に作る理由と`AbstractUser`の継承
- ReactとDjango REST APIの役割分担
- PostgreSQLから日、週、月の学習時間を集計する方法
- 学習記録と振り返りを利用者ごとに分離する方法
- WebページやPWAから現在のウィンドウを確実に自動終了できない理由
